## Native placement and deferred close follow-up

[The second PR #107 review](https://github.com/scholay/rimes/pull/107#discussion_r4206723250)
found that native caption movement could raise Buffer without a Runtime update.
The regression executes native `HWND_TOP` and `HWND_TOPMOST` placement and samples
order, style, activation and geometry in one fixture UI dispatch. Previous
production `0478e08` with this new test reproduces the missing invariant: x64
exit 1 contains exactly the two expected placement/geometry-order failures,
with no unexpected failure. The test driver uses the same PMv2 DPI context as
the production window; it also verifies `SWP_NOZORDER` preserves requested move
and resize coordinates.

Commit `122febd` constrains the insertion anchor during `WM_WINDOWPOSCHANGING`,
retaining geometry flags and `DefWindowProc` processing. Both architectures
built, and the new atomic placement checks passed on x64. The full x64 suite
then passed 21/22 groups: Settings UI still failed its two original hidden/visible
close-restoration assertions. x86 CTest was not run in that failed attempt.
The failure and task result 1 are preserved rather than counted as success.

A bounded temporary diagnostic of that exact source observed successful
`SetWindowPos` returns during the Settings destruction callback with no
`WM_WINDOWPOSCHANGED` and no TOPMOST style change. The same helper on a later
Runtime dispatch committed the style. The evidence does not claim to establish
Windows' internal reason. The temporary trace was removed, its limited
interactive task was removed with result 0, and all 284 source hashes were
restored before the final overlay.

Final production commit `9fd1e720e632d03cc85eb61b0c4e482c0b39cb18` posts a
private UI message when Settings closes and recomputes current Settings and
teardown state when that message runs. Reopening before a queued restoration
therefore keeps Buffer behind the new Settings. The new regression posts close
and a queue barrier; it checks hidden/visible restoration without a Runtime
notification, and queues reopening before the close message's restoration.
All original content, capture, frozen-request, visibility and noactivation checks
are retained. A second x64 negative control (production `122febd` with the final
regression alone) reproduces the barrier and original restoration failures;
there are no unexpected failure labels.
